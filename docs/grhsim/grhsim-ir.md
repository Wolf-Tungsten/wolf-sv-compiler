# GRHSIM IR

> 状态：新架构文档。本文定义 GRHSIM IR 的定位、组成与核心思想，说明它如何
> 完整表达 [GRHSIM 仿真模型](grhsim-simulation-model.md) 中的仿真对象
> ⟨S, S_edge, G⟩。数据类型系统的两轨框架在第 3 节；本文不定义具体操作，
> 操作按方言组织，由 [dialect/](dialect/) 下的方言文档分别定义。

## 1. 定位

仿真的本质是对数据流图的反复求值：eval 每一轮按依赖顺序遍历全图，直至
不动点（仿真模型第 5 节）。因此 GRHSIM IR 与 GRH IR 同为图结构 IR——顶
点为操作、边为数据流。GRHSIM IR 由 GRH IR 映射（lowering）得到，是仿真
流水线中承载一切优化与后端代码生成的单一 IR：

```text
GRH IR → GRHSIM IR →（图上的优化操作）→ 后端代码（C++ / LLVM IR / …）
```

与 GRH IR 的区别：

- **层次消除**：GRH IR 描述设计的层次结构（模块、`kInstance`、XMR）；
  GRHSIM IR 面向执行，层次在映射时全部展开为单一扁平图。仿真语义只定义
  在扁平图上，模型不感知层次。
- **面向仿真性能**：GRH IR 的操作集合忠实对应 SystemVerilog 语义；GRHSIM
  IR 允许更丰富、更贴近执行的操作（复合操作、后端专属操作），其操作集合
  随方言扩展（第 5 节）。整数组读写、packed 视图批量操作等仿真导向操作
  即为典型：它们只应由 GRHSIM IR 上的变换产生，见
  [generic 方言](dialect/generic.md) 3.4 节。

## 2. IR 组成：完整表达仿真模型

一份 GRHSIM IR 模块完整描述一个仿真对象 `Sim = ⟨S, S_edge, G⟩`：

```text
Module = ⟨StateDecl, TrackSet, G = ⟨V, E, H⟩, Schedule⟩
```

- **StateDecl**：`S = (S_in, S_out, S_state)` 的结构声明——逐标识符给出
  名称、类型与初始化属性（第 3 节）。状态的值属于运行时，IR 只声明其结
  构。
- **TrackSet**：被跟踪信号集，即 `S_edge` 的键集。
- **G = ⟨V, E, H⟩**：操作图与 host 调用表，与模型中的定义一致。顶点为
  操作 op，边为数据流；`H` 的条目记录宿主例程的标识、参数签名与绑定，
  需要宿主能力的 op 引用条目索引。
- **Schedule**：调度信息——图划分与执行顺序（第 4.2、4.3 节）。初始映射
  得到的是未调度图；调度 pass 把结果物化在 IR 中，emitter 只消费调度结
  果。

图的语义（轮、快照、不动点、边缘跟踪）不在本文重复，一律以仿真模型文
档为准：GRHSIM IR 是模型的语法表达，不引入模型之外的语义。

## 3. 数据类型系统

仿真模型把 `S`、`S_edge` 定义为标识到逻辑值的映射，不规定逻辑值的编码
与存放方式（模型第 2、6 节）。GRHSIM IR 以两轨并行的数据类型系统建模
这一点：generic 数据类型系统与后端特化数据类型系统并行，统一覆盖状态
与数据流边上的值。generic 类型清单见 [generic 方言](dialect/generic.md)
第 2 节，各后端的类型清单由各后端方言文档定义。

### 3.1 两轨并行

**generic 类型系统**：语义类型，后端无关：逻辑向量 `logic<W, s>`、存储
器数组 `array<row, logic<W, s>>`，以及仅用于 host 调用的 `real`、
`string`。op 的语义只定义在 generic 类型上。

**后端类型系统**：每个后端方言（`cpu.*`、`corvus.*`）各自定义一套类型，
描述物理表示——值编码（两态/四态、机器字打包）与存储布局（独立槽位、
数组摊开、多个信号合并到一个机器字、一个宽信号拆到多个字等）。各后端
的类型系统相互独立，互不复用。

两轨的关系：

- generic 类型是语义基准，后端类型是表示选择。**精化关系**：每个后端类
  型必须声明它实现的 generic 类型；任何值——无论取哪一轨的类型——因
  此都有明确的语义读法。
- 与 op 的最小集合性质一致（第 5 节）：后端类型系统只补充 generic 类型
  无法表达的表示类型，不重复定义语义类型。后端模块的类型全集 =
  generic 类型 ∪ 本后端类型，与图上 op 的混合方式相同。
- 后端方言 op 的语义必须等于在所实现的 generic 类型上的对应语义。

### 3.2 状态的类型：StateDecl 双标注

```text
StateEntry = ⟨name, kind, genType, init, backendType?⟩

kind ∈ {in, out, state}        -- 三个名字空间互不相交
```

- `name`：标识符，模块内唯一；
- `kind`：属于 `S_in`、`S_out` 还是 `S_state`；
- `genType`：generic 类型。语义标注，恒定保留，不被特化覆盖；
- `init`：初始化属性，以 generic 类型表达（generic 方言第 7 节）；
- `backendType`：后端类型，可选。初始映射时缺省，表示取 generic 类型的
  平凡布局；存储特化 pass 填入（3.5 节）。

`S_edge` 不设独立声明：TrackSet 由图上 op 的事件属性派生（generic 方言
第 5 节），其条目的类型与被跟踪信号一致，随信号一同特化。

### 3.3 数据流边的类型：随 op 方言

- 每条边（op 结果）携带一个类型，取自两轨之一，由产生它的 op 的方言决
  定：generic op 产 generic 类型的值，后端 op 产后端类型的值。
- 与状态不同，边上只标单类型，无双标注：其语义由精化关系给出（3.1 节），
  已足够明确。
- 子图替换改变 op 方言时，边上类型随 op 一并改写；不存在独立的"边类型
  pass"。
- 方言混合处（generic op 消费后端类型的值，或反之）的衔接规则——直接
  消费还是经显式转换 op——由后端方言文档定义。

### 3.4 对应关系与合法性

后端类型对它实现的 generic 类型必须满足：

- **保语义**：对设计实际出现的值域，编码/解码无损。两态编码仅在设计运
  行中不产生 X/Z 时合法（generic 方言第 2 节）。
- **布局自由**（状态）：一个状态可拆到多个物理字（一对多），多个信号也
  可合并进一个物理字（多对一）；合并时各条目的 `backendType` 共享同一
  槽位描述。布局变化引起的读写改写属子图替换（4.1 节），由特化 pass 把
  generic 读写 op 重写为后端方言的访问/位操作 op。

### 3.5 特化流程

```text
StateDecl（仅 generic 类型）+ 图（generic op，generic 类型的边）
  │  存储特化 pass：逐状态条目选定 backendType，同步改写读写 op 为后端方言
  │  方言下降 pass：把计算子图重写为后端方言 op，边上类型随之改写
  ▼
StateDecl（generic + backend 类型）+ 图（两轨 op 与边类型混合）
```

- 特化粒度逐条目独立：可以只特化一部分状态，其余保持 generic 平凡布局。
- `S_in`、`S_out` 条目的 `backendType` 即仿真对象的对外 ABI：调用方按此
  布局驱动输入、采样输出。
- `init` 的语义不变；特化只改变其在 Sim 构建时的物理写入形式。

## 4. 图上的三类操作

一切仿真优化都可以归类为对 GRHSIM IR 图的三种操作。每种操作都是显式
pass，操作结果直接物化在 IR 上。

### 4.1 子图替换

把 `G` 中的子图 `g` 替换为仿真行为等价、但性能更优的 `g'`。

等价的含义：对任意输入激励，替换前后 eval 返回的稳定状态与 host 副作
用的可观察序列相同；中间迭代轮次的行为允许不同。

典型例子：常量折叠、死代码消除、操作融合、强度削减、存储布局改写。

### 4.2 图划分

把 `V` 划分为互不重叠的区域（region）。区域是仿真中的激活单位：每轮
先判定区域的激活条件，为真则区域内 op 按序全部执行，为假则全部跳过。

区域被跳过时，其跨出区域边界的边的值保持为上一次激活时的结果，下游区
域读到的仍是旧值；区域内不产生状态写出与 host 调用。这与模型"每轮每
op 恰好求值一次"不冲突：未激活区域的 op 视为求值为保持。跨出区域边界
的边因而与破环边（4.3 节）一样跨轮保存，emit 时为其分配存储。

- 激活条件是区域的属性，引用边缘事件（如信号 `i` 的上升沿）或恒真
  （每轮必做）；具体形式由方言文档定义。
- 合法性：一个强连通分量不得被切分到多个区域，否则区域间无法排定执
  行顺序（4.3 节）。

划分让与当前求值无关的代码整片跳过，是条件执行类优化（如时钟沿触发
的提交逻辑）的表达基础。

### 4.3 顺序调度

调度为 op 的执行顺序赋值，分两个粒度：

- **区域内**：op 的全序，须与区域内部的数据依赖一致。
- **区域间**：偏序（区域依赖图）。跨区域的数据流边产生顺序约束；相互
  无约束的区域可以任意次序执行，也可以并行执行——区域间的并行执行由
  偏序表达。

区域依赖图必须无环；由 4.2 的合法性约束（不切分强连通分量），无环性
自动成立。

GRHSIM IR 不为 host 副作用定义额外的顺序：副作用的可观察顺序应在调度
之前解决。例如同一时钟域激活的多个 `$display`，应在生成 GRH IR 时就按
顺序拼接成单个 display op；到 GRHSIM IR 这里，每个副作用 op 都是原子
操作，调度只需遵循数据依赖，不另行排序。

调度还须满足仿真模型对一轮求值顺序的要求（模型 5.1 节）：全图 op 序
展开后是 `(V, E)` 商图拓扑序的线性延拓。破环边集合随调度确定，其上的
值跨轮保存（模型中的 `W`），emit 时为其分配存储。

## 5. 方言

GRHSIM IR 的操作按方言（dialect）组织，记作 `方言名.op名`：

- `generic.*`：初始方言。从 GRH IR 映射得到的操作集合，后端无关，语义
  通用。
- `cpu.*`：CPU 软件仿真后端的专属操作。
- `corvus.*`：未来的 corvus 加速器后端的专属操作。

方言满足**最小集合性质**：扩展方言不重复定义 `generic.*` 已有的操作，只
补全 `generic.*` 无法表达、且该后端必需的新操作，保证总操作数尽可能少。

优化与 lowering 体现为方言间的逐步改写：初始图全部使用 `generic.*`，
各 pass 按后端需要把子图重写为后端方言操作（属于 4.1 节的子图替换）；
未被重写的部分保持 `generic.*` 不变。因此后端图是 `generic.*` 与后端方
言的混合，`generic.*` 是公共基底，各后端都必须支持。各方言的 op 集合、
操作数与语义由 [dialect/](dialect/) 下的方言文档定义（模板见
[dialect/dialect-template.md](dialect/dialect-template.md)）。

## 6. CPU 软件仿真器流程构想

面向 CPU 后端，从 GRH 到可执行代码的完整流程：

```text
GRH IR
  │  映射：层次展开，逐操作直译
  ▼
GRHSIM IR（generic）
  │  显式 pass：子图替换（优化）、存储布局具体化、图划分、顺序调度、
  │              generic → cpu 方言下降
  ▼
GRHSIM IR（cpu，已调度）
  │  emit：按调度结果逐 op 打印
  ▼
C++ 代码 / LLVM IR
```

核心原则：**一切优化都是显式 pass**。emitter 不做任何优化决策，只按 IR
中物化的调度顺序逐个打印 op——不像旧 GRHSIM-AM 方案那样把调度、融合等
逻辑藏在 emitter 内部。这保证优化可独立测试、可自由组合，且任意 pass
之间的中间结果都可以 dump 检查。典型的 pass 编排方案见
[flow/](flow/) 目录。
